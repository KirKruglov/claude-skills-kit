# Cowork Plugin Audit — Руководство пользователя

Как использовать Cowork Plugin Audit: чистка плагинов, снижение расхода токенов, оптимизация Cowork-сессий.

---

## Быстрый старт

Самый короткий путь к результату:

1. Напиши: «Аудит плагинов»
2. В одном сообщении опиши роль и 2–3 основные задачи (например, «Я PM, пишу спеки и веду спринт-планирование»)
3. Вставь список установленных плагинов по запросу
4. Получи таблицу аудита с рекомендациями: оставить / отключить

**Результат:** Чёткая таблица — какие плагины оставить, какие отключить, почему.

**Время:** ~3 минуты

---

## Сценарии

### Сценарий 1: Чистка после массовой установки плагинов

**Ситуация:**
Ты — контент-маркетолог, который при настройке Cowork установил все доступные плагины «на всякий случай». Через три недели замечаешь, что сессии стали медленнее, а ответы иногда ссылаются на инструменты, которыми ты никогда не пользуешься. Твои реальные задачи: написание текстов, управление контент-календарём и синтез исследований.

**Что делать:**

1. Запусти скил: «Аудит плагинов» или «Какие плагины отключить»

2. Опиши workflow в одном сообщении:
   - «Я контент-маркетолог. Пишу статьи, веду контент-календарь, синтезирую исследования. Продажами, финансами и разработкой не занимаюсь.»

3. Вставь список установленных плагинов по запросу:
   - Пример: `product-management, engineering, sales, data, finance, operations, skill-planner`

4. Изучи таблицу аудита:
   - Колонка **Рекомендация** — плагины с пометкой `disable` можно отключить прямо сейчас
   - Плагины `disable-until-needed` — отключи до следующего профильного проекта

5. Перейди в Настройки Cowork → Плагины и отключи отмеченные плагины

**Ожидаемый результат:**

Получаешь таблицу с классификацией каждого плагина и объяснением, почему он соответствует или не соответствует workflow. Итоговый блок показывает счётчики и оценку «умеренное снижение токен-расхода». Опциональный блок Project Instructions — готовый текст для вставки в настройки проекта.

**Почему это работает:** Удаление idle-плагинов уменьшает количество скилов, загружаемых в контекст каждой сессии. Меньше нерелевантных инструментов — быстрее и точнее ответы, ниже расход токенов.

### Сценарий 2: Запуск нового проекта с другим фокусом

**Ситуация:**
Ты разработчик, который в основном использует плагин `engineering`. Тебя назначили вести кросс-функциональную инициативу: спринт-планирование, обновления для стейкхолдеров, трекинг рисков — всё это задачи продуктового менеджера. Хочешь временно добавить `product-management` и провести аудит под новый контекст.

**Что делать:**

1. Установи плагин `product-management` в настройках Cowork

2. Запусти скил: «Аудит плагинов» или «Проверь мою конфигурацию Cowork»

3. Опиши новый контекст:
   - «Ближайшие 3 месяца я веду кросс-функциональную инициативу: спринт-планирование, написание апдейтов для стейкхолдеров, трекинг рисков, анализ метрик. Иногда — код-ревью, активной разработки нет.»

4. Вставь полный список плагинов: `engineering, product-management, data, sales, finance`

5. Изучи вывод:
   - `product-management` → вероятно, `core` для этого проекта
   - `engineering` → вероятно, `contextual` (редкое ревью кода)
   - `sales`, `finance` → вероятно, `idle` → `disable`

6. Скопируй опциональный блок Project Instructions в файл инструкций проекта

**Ожидаемый результат:**

Получаешь проектный аудит, подтверждающий соответствие конфигурации плагинов новой инициативе. Блок Project Instructions — страховка от случайной активации `sales` или `finance` во время сессий планирования.

**Почему это работает:** Контекст плагинов должен следовать контексту проекта. Аудит в начале проекта гарантирует, что активны только нужные инструменты.

### Сценарий 3: Плановый квартальный ревью

**Ситуация:**
Ты фриланс-консультант, который работает по нескольким типам проектов: маркетинг, операции, продуктовый консалтинг. Со временем список «всегда активных» плагинов вырос до 7 позиций. Хочешь провести квартальную чистку и разделить плагины на «всегда нужны» и «нужны только для конкретного типа проекта».

**Что делать:**

1. Запусти скил: «Аудит плагинов»

2. Опиши общий кросс-проектный workflow:
   - «Я работаю по трём типам проектов: контент-маркетинг, оптимизация операций, продуктовый консалтинг. Основные задачи: написание отчётов, проведение воркшопов, синтез исследований.»

3. Вставь полный список плагинов: `product-management, operations, sales, data, engineering, finance, skill-planner`

4. Изучи аудит:
   - Плагины `contextual` — кандидаты на глобальное отключение с реактивацией по типу проекта
   - Плагины `idle` — кандидаты на постоянное удаление

5. Примени рекомендации:
   - Отключи `idle`-плагины насовсем
   - Для `contextual`-плагинов зафиксируй, для каких типов проектов они нужны

**Ожидаемый результат:**

Получаешь глобальный аудит, разделяющий постоянно нужные инструменты и инструменты для конкретных типов проектов. Итог помогает сформировать базовый набор «всегда активных» плагинов и чеклист для проектного онбординга.

**Почему это работает:** Кросс-проектные пользователи накапливают плагины, нужные только для одного типа клиентов. Аудит делает этот паттерн видимым и даёт структурированный способ управлять ротирующимся набором инструментов.

## Советы

### Совет 1: Описывай задачи, а не инструменты

При описании workflow фокусируйся на том, что *делаешь* (пишу спеки, ревьюю код, отслеживаю KPI), а не на том, какими инструментами пользуешься. Скил сам сопоставит задачи с плагинами.

**Про-тип:** Если не можешь описать задачи в 2–3 предложениях — аудит пока преждевременен. Сначала сформулируй фокус текущего проекта.

### Совет 2: Перезапускай аудит при смене проекта

Рекомендации аудита актуальны только для описанного тобой workflow. При старте нового проекта или смене фокуса — запусти аудит заново. 5-минутный пере-аудит в начале проекта экономит токены на протяжении недель.

### Совет 3: Используй блок Project Instructions как страховку

Если скопировать сгенерированный блок Project Instructions в настройки проекта, Claude не будет активировать скилы отключённых плагинов, даже если триггерная фраза случайно совпадёт. Особенно полезно для плагинов с широкими триггерами — `sales`, `engineering`.
