# Feature Announcement Writer — Руководство пользователя

Практические сценарии: как превратить описание фичи в готовый пакет анонса.

---

## Быстрый старт

Самый быстрый путь к результату:

1. Напишите или вставьте 1–2 абзаца описания фичи
2. Скажите: "Напиши анонс фичи" и вставьте текст
3. Получите 4 готовых блока: changelog, email, push, пост

**Результат:** Полный пакет анонса, который можно скопировать в каждый канал напрямую.

**Время:** ~2 минуты

---

## Сценарии

### Сценарий 1: PM запускает фичу без маркетинговой команды

**Ситуация:**
Вы только что выпустили новую фичу. Маркетинга нет — нужно самостоятельно написать анонс для changelog, email, Notion и LinkedIn. На это 20 минут до стендапа.

**Что делать:**
1. Активируйте скил и скажите: "Напиши анонс фичи"
2. Вставьте описание фичи (черновик тоже подойдёт)
3. Если скил спросит название продукта или аудиторию — ответьте в одном сообщении
4. Скопируйте 4 блока вывода в соответствующие места:
   - Changelog entry → вставить в CHANGELOG.md
   - Email → вставить в почтовый клиент, проверить тему, отправить
   - Push → вставить в инструмент in-app сообщений
   - Пост → вставить в LinkedIn или X

**Ожидаемый результат:**
Четыре текста, каждый адаптирован под ограничения своего канала: 160 символов для push, hook-first для поста, benefit-first тема для email. Генерируется за минуту.

---

### Сценарий 2: Анонс бета-фичи для ранних пользователей

**Ситуация:**
Вы выкатываете фичу в бету для ограниченной аудитории. Нужен текст, который честно отражает статус бета, создаёт интерес и не обещает лишнего. Аудитория — опытные пользователи, записавшиеся на ранний доступ.

**Что делать:**
1. Скажите: "Создай пакет анонса"
2. Опишите фичу и добавьте: "Это бета-запуск, только для ранних пользователей"
3. Скил определит бета-контекст и:
   - Добавит `[Beta]` в changelog
   - Оформит email в стиле "вы в бета-группе"
   - Сделает push коротким и энергичным
   - Напишет пост в формате приглашения ("кто хочет попробовать?")

**Ожидаемый результат:**
Бета-подходящие тексты во всех 4 форматах с согласованным мессенджингом.

### Сценарий 3: Адаптация технического описания для пользователей

**Ситуация:**
Разработчик написал технически точное описание фичи — с API-терминами и деталями реализации. Нужен user-facing текст, а не техническая документация.

**Что делать:**
1. Вставьте описание разработчика как есть
2. Если скил пометит текст как технический — ответьте "user-facing" для подтверждения
3. Скил извлечёт пользовательскую ценность и напишет текст простым языком

**Ожидаемый результат:**
User-facing тексты, которые переводят технические детали в конкретные пользовательские преимущества. Что делает код → что теперь может пользователь.

---

## Советы

**1. Чем конкретнее ввод, тем лучше вывод.**
"Добавили экспорт" — слишком расплывчато. "Пользователи теперь могут экспортировать любой дашборд в PDF одним кликом прямо из шапки страницы" — даёт скилу достаточно для написания специфичного, benefit-first текста.

**2. Используйте дефолты для скорости, переопределяйте только когда нужно.**
Аудитория по умолчанию — `users`, тип запуска — `GA`. Если пишете для корпоративных клиентов или бета-группы — уточните. Формулировки изменятся существенно.

**3. Запрашивайте blog intro только если он нужен.**
Скил предложит написать вводный абзац для блога в конце каждого вывода, но не сгенерирует его автоматически. Это сохраняет дефолтный вывод сфокусированным и быстрым.
